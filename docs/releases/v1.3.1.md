# v1.3.1 — Fix Usage browser Close surviving host dialog lifecycle

Patch release that fixes a `v1.3.0` regression where every `× Close` and `Escape` in the Usage browser became a no-op after first paint. No new features, no API changes — the same `v1.3.0..603994a` hotfix already on `main`, now curated as `1.3.1`.

## What changed

### Usage browser Close now survives host replace → previous onClose

`v1.3.0` shipped the browser's loading → provisional (eligible `≤100 ms`) → final (`V2 session.list({project, limit:1})` with `BROWSER_CONCURRENCY` 4 + `FETCH_TIMEOUT_MS` 4s, `58→30` calls at `N=28`) paint sequence. Each content update reused the same idempotent `close` callback as the host `onClose` passed to `api.ui.dialog.replace(render, onClose)`. OpenCode `1.18.23`'s `DialogStack` (`packages/tui/src/ui/dialog.tsx`) invokes the *previous* stack entry's `onClose` before both `replace()` and `clear()` — so every provisional and final `replace` fired that close, set `closed = true`, and left the later user `× Close` selection and the host `Escape → onClose` path with nothing to clear. Root, Project detail, and Session detail were all affected; the dialog appeared stuck open.

`v1.3.1` separates the host lifecycle (`onClose`) from the user action (`close`) in `browser-activity.ts` (`BrowserActivity` for the root) and in the local `project-dialog.tsx` / `session-dialog.tsx` dialogs. `onClose` is now `if (suppress) return; close()`, and every content-update `replace` runs inside `withSuppress(() => dialog.replace(render, onClose))` so only those replace-driven callbacks are suppressed — a real user `× Close` and a real `Escape` still call `close()` exactly once, are idempotent (`closed` guard), clear the stack via `dialog.clear()`, and block late async `replace` via the existing `isActive()/closed` generation guard so a delayed probe cannot reopen a closed browser. ([#113](https://github.com/jonasotoaguilar/opencode-tokenmeter/pull/113)) which landed as `603994a21c1527e72a5da2d3086690918d78331e`.

### Verification of the contract

The regression is covered by the real-host harness `test/browser-close-realcontract.test.ts` which faithfully replays `replace`/`clear → previous onClose` per `dialog.tsx`: root `Close` after provisional + final replaces, Project detail `Close`, Session detail `Close`, `Escape`-equivalent `onClose`, and `Close` during loading preventing late async reopen. Baseline on the `v1.3.0` tag fails `4/5`; candidate at `603994a` passes `5/5`. Full suite `369` tests pass; the one-file `v1.3.1` notes, `1.3.0 → 1.3.1` bump, and layered docs are the only authored delta.

## Upgrade

From `1.3.0` (or any earlier stable):

- **Unpinned (bare) entry** `opencode-tokenmeter-tui` / `opencode-tokenmeter-tui@latest` — remove the bare cache directory and restart OpenCode; it reinstalls `1.3.1` automatically:

```bash
rm -rf ~/.cache/opencode/packages/opencode-tokenmeter-tui@latest
```

Then restart OpenCode. No config change, no version to remember, nothing accumulates.

- **Pinned to `1.3.0`** (`opencode-tokenmeter-tui@1.3.0` in `tui.json`) — remove that version's cache directory, update the pin to `1.3.1`, and restart. The directory is named after the config entry, so `rm -rf ~/.cache/opencode/packages/opencode-tokenmeter-tui@1.3.0` forces a fresh install on next start into the same directory (verified per `packages/core/src/npm.ts` cache-first `Npm.add` and `packages/opencode/src/plugin/shared.ts` / `plugin-loading.md` — no TTL, no auto-update; the cache-removal step *is* the update flow, see `skills/opencode-plugin/references/updating-plugins.md`):

```bash
rm -rf ~/.cache/opencode/packages/opencode-tokenmeter-tui@1.3.0
```

Then set the entry to `opencode-tokenmeter-tui@1.3.1` (or to the bare name to track `latest`) and restart OpenCode. If the `dist/tui.js` artifact appeared stale after an upgrade, `bun run build` was the documented remediation and remains so.

```json
{
  "$schema": "https://opencode.ai/tui.json",
  "plugin": ["opencode-tokenmeter-tui@1.3.1"]
}
```

Or keep the bare entry to always reinstall the latest published version after the same `rm -rf …@latest` + restart flow.

## Rollback

`1.3.0` remains a fully loadable published version. If `1.3.1` regresses:

- **Users**: pin back to `1.3.0` in `tui.json` and remove that version's cache directory, or remove the plugin entry, and restart; report the failure so a `1.3.2` can be cut.
- **Maintainer**: the release pipeline is tag-driven (`v1.3.1` → preflight → publish → verify). A regression is corrected by cutting the next patch tag, not by re-pointing `1.3.1` — npm versions are immutable. Keep this document as the single release record until the next tag renames it.
