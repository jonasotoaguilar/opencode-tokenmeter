# v1.4.0 — Durable per-session checkpoints outside disposable state

Minor release that moves Project and browser usage from the disposable host state directory into a per-OS durable store. Each session keeps one checkpoint row reconciled monotonically, so Project and browser historical totals survive cache wipes, restarts, and worktree renames. No breaking API or config changes; v1.3.1 data is imported once.

## What changed

### Durable per-session checkpoints in OS data directory

Usage is now stored per session in `checkpoints.sqlite` under the OS data directory — `$XDG_DATA_HOME/opencode-tokenmeter` (Linux), `~/Library/Application Support/opencode-tokenmeter` (macOS), `%APPDATA%\opencode-tokenmeter` (Windows) — resolved by `src/tokenmeter/durable/paths.ts` (`resolveDurableDir`/`durableDbPath`). Override with `TOKENMETER_DURABLE_DIR` (absolute, safe-checked). Paths normalize per platform (`posix`/`win32`) with realpath canonicalization (non-Windows) and reject filesystem roots and the home directory. The DB is created with `PRAGMA journal_mode=WAL`, `busy_timeout=5000`, `synchronous=NORMAL`, directory `0700`, file `0600`, one row per `(session_id, project_id)` plus `project_alias` for worktree recovery. Indexes on `project_id` and `project_alias`.

### WAL and monotonic reconciliation (no extra SDK calls)

The checkpoint refresh is piggybacked on the successful `client.session.list({directory, scope:"project", limit:10000})` that already powers the Project section — no extra message sweeps or separate SDK calls. `checkpointActiveProject` (`src/tokenmeter/durable/checkpoints.ts`) builds live rows via `mergeRows` and UPSERTs only changed sessions in one WAL `immediate` transaction; an unchanged idle refresh produces zero row updates (`rowsEqual` guard). Per-field merge is high-water monotonic: `MAX(input)`, `MAX(output)`, `MAX(reasoning)`, `MAX(cache_read)`, `MAX(cache_write)`, recomputed `cache` and `context`; cost provenance preserves `reported`/`observed` over `estimated` (max wins when both are strong, strong wins over weak, otherwise max). `reconcileProjectUsage` (`src/tokenmeter/durable/reconcile.ts`) counts each session ID exactly once — live-only, checkpoint-only (historical), or merged live+checkpoint with monotonic per-field MAX — never double-counted and never a live total plus a deleted aggregate.

### One-time legacy aggregate migration

Upgrades that still have the prior aggregate DB (`tokenmeter.sqlite` under `api.state.path.state`, via `src/tokenmeter/durable/legacy-path.ts`) import once on first successful Project refresh. `migrateLegacyAggregates` (`src/tokenmeter/durable/migrate.ts`) reads the single-row-per-`project_id` aggregate (`cost,input,output,reasoning,cache_*`) and inserts one reserved checkpoint per project (`session_id="__migrated_aggregate__"`) only when absent. The import is idempotent and fail-contained; after import the durable path is the sole reader/writer — no ongoing dual-write. If the legacy file was already deleted there is nothing to recover and no error is surfaced.

### Project and browser recovery

Project (`src/tokenmeter/project.ts`: `refreshProject`) and browser (`src/tokenmeter/browser/projects.ts`: `loadBrowserProjects`, plus project/session detail) now read durable checkpoints and reconcile via the durable union. Browser loads fail-closed: `null` from `fetchSessionsForBrowse` (transport/error/truncated) throws and surfaces the error, never silently falling back to checkpoint-only; only a successful empty `[]` (cache wipe) may be complemented by historical checkpoints. Alias normalization (`normalizeAlias`) stores canonical worktree/directory paths so `project_id` mismatches and renames recover correctly (live `projectID` mismatch is filtered, checkpoint `project_alias` match recovers). Platform paths handle Windows case-insensitive comparison.

### Observed message-derived Project cost

Project checkpoints now merge the complete observed aggregate derived from authoritative session messages (`observedSessionUsage`/`observedToEntry` in `src/tokenmeter/durable/merge.ts`) for each session ID present in the successful project list before the durable batch UPSERT. Only IDs in that successful list are considered; historical checkpoint-only IDs are untouched until they reappear. Each session merges independently — no tree total. Because the observed aggregate is the full per-session spend reconstructed from all assistant messages (including per-component high-water), a smaller partial `reported`/`estimated` list aggregate cannot undercount it (`mergeCost` strong-source rule). `checkpointDeletedSession` (`src/tokenmeter/durable/deleted.ts`) likewise merges payload plus observed high-water before the final flush on `session.deleted`.

## Compatibility

Additive, backwards compatible. No config schema, TUI contract, or plugin API change. Existing installs keep working after the one-time migration. Durable store lives outside the host state directory so future OpenCode cache clears do not erase history. No manual file migration is required; do not copy `tokenmeter.sqlite` by hand.

## Upgrade

From `1.3.1` (or any earlier stable) on the same plugin entry mechanism as documented in `skills/opencode-plugin/references/updating-plugins.md`:

- **Unpinned (bare) entry** `opencode-tokenmeter-tui` / `opencode-tokenmeter-tui@latest` — remove the bare cache directory and restart OpenCode; it reinstalls `1.4.0` automatically:

```bash
rm -rf ~/.cache/opencode/packages/opencode-tokenmeter-tui@latest
```

Then restart OpenCode. No config change.

- **Pinned to `1.3.1`** (`opencode-tokenmeter-tui@1.3.1` in `tui.json`) — remove that version's cache directory, update the pin to `1.4.0`, and restart:

```bash
rm -rf ~/.cache/opencode/packages/opencode-tokenmeter-tui@1.3.1
```

```json
{
  "$schema": "https://opencode.ai/tui.json",
  "plugin": ["opencode-tokenmeter-tui@1.4.0"]
}
```

Or use the bare entry to track `latest`. The first Project load after upgrade triggers the one-time legacy import if the legacy DB still exists.

## Rollback

`1.3.1` remains a fully loadable published version on npm. If `1.4.0` regresses:

- **Users**: pin back to `1.3.1` in `tui.json`, remove that version's cache directory (`rm -rf ~/.cache/opencode/packages/opencode-tokenmeter-tui@1.4.0`), and restart; or remove the entry and restart. The durable `checkpoints.sqlite` is additive and does not interfere with older code reading the legacy aggregate. Report the failure so a `1.4.1` can be cut.
- **Maintainer**: the release pipeline is tag-driven (`v1.4.0` → preflight → publish → verify). A regression is corrected by cutting the next semver tag, not by re-pointing `1.4.0` — npm versions and Git tags are immutable. Keep this document as the single release record until the next tag renames it via `git mv`.
